## Connive: a bug we inherited, found only because the user asked

The user mentioned hearing connive was broken. Three connive cards are in our
pool (Illuminator Virtuoso, Ledger Shredder, Lethal Scheme). The break is
**not** #11388 (the connive AI commit deliberately excluded by the pin) — it
came in via `28431f2647` **"Recruit: add Effect" (#11355)**, whose title
mentions neither connive nor a bug.

`SpellAbilityEffect.discard()` writes the post-move collection back into the map
it is handed (`:906`) so its own `DiscardedAll` loop can read it. #11355 changed
`ConniveEffect` to pass an immutable `Map.of(...)`, so every connive resolution
throws. `RecruitEffect`, added by the same PR, shipped with the identical bug.

Cost: **a full 4,000-game arms read.** 28 `UnsupportedOperationException`
crashes in 2,000 games (1.4%) against 4 in all pre-rebase history, concentrated
in the five pool decks carrying connive cards — a per-matchup bias, not uniform
noise. Fixed at both sites, pinned by `ConniveDiscardMapTest` validated failing
first. Post-fix: 0 UOE in 2,000 games.

**Deliberately not upstreamed.** Hanmac took responsibility and is fixing it; no
caller of `discard()` reads the map back, so every plausible maintainer fix is
behaviorally identical to ours. The commit message carries the instruction to
drop ours at the next rebase.

## The re-baseline, and what it cost to learn

Four 2,000-game Ante-corrected reads, run sequentially at matched load:

| | old engine | new engine | Δ |
|---|---|---|---|
| RL `run7b-i14` | 0.5530 ± 0.0109 | **0.5121 ± 0.0110** | −4.09 ± 1.55 (t=−2.64) |
| BC `d5-combat` | 0.4616 ± 0.0109 | **0.4452 ± 0.0109** | −1.64 ± 1.54 (t=−1.06) |

- **RL over BC survives: +6.69pp ± 1.55 (t=+4.32)** on the new engine. The core
  M2/M3 claim holds; ckpt of record unchanged.
- **Against the heuristic the agent is at parity: +1.21pp ± 1.10.** ADR-0019 and
  ADR-0023's "first teacher-surpassing read" was measured against the *old*
  heuristic.
- **DiD −2.45pp ± 2.19 (t=−1.12): not significant.** The control was run
  specifically to separate uniform-shift from RL-specific and it does not do so.
  Stacking two differences inherits SE 2.19pp — arithmetic that belonged before
  the runs, not after. Called decisive in advance; it wasn't.

Leading explanation, and the user's read: the heuristic got stronger (26
`forge-ai` commits; maintainers actively tuning). Supported by BC's
first-attempt veto *falling* 0.1395→0.1072 — actions land more easily, the
opponent just plays better.

## Learner speed: measured, diagnosed, not yet fixed

Benchmark on a quiet GPU (`scripts/bench_learner.py`, run-8 iter-005 replayed):
throughput **flat in `--seg`** (64/128/256/512 → 0.410/0.442/0.419/0.423
traj/s) and **worse with more workers** (6→12 = 0.442→0.391), GPU busy ~10%.
Both hypotheses dead. Phase instrumentation: **load 86.9%**, fwd_nograd 5.7%,
fwd_bwd 3.7%. Process sampling: main process 83% CPU *while waiting*, six
workers idle at 23–33%, box at load 1.5/32.

Cause: `RlTrajectories` yields per-window example dicts and `collate` runs
main-process-side, so each trajectory ships thousands of small tensors through
the DataLoader shm+pickle path to a single consumer. Fix designed, not built:
collate inside the worker — and pre-collating at the current seg chunking makes
the segmentation identical, so a **strict byte-identical equivalence gate** is
available rather than a tolerance argument.

Corollary: the VRAM elasticity work bought robustness, not speed. Run-8 spending
44h at `seg 128` cost nothing measurable.

## What broke in my process (worth more than the bugs)

- **A crash class is a stack trace, not an exception type.** I dismissed the
  first connive crash as pre-existing because the exception *type* had 4
  historical occurrences. That shortcut cost the 4,000-game read.
- **Verify the instrument before trusting a gate.** My first "pool smoke gate"
  silently ran `--bridge local-random` (the harness default) with one worker
  (`chunk=200 ≥ 120 games`). Its alarming numbers were properties of the random
  arm. `forge census` was the right instrument and had a recorded baseline.
- **Arm the watcher in the same action as the launch.** Two ~2h reads went out
  detached with nothing watching, so completion reached nobody and the user had
  to ask whether notifications were broken. They weren't. Memory note updated.
