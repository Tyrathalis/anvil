# 2026-07-31: d6-run10 crash forensics + resume (iter-9 drill-ingest cascade)

## What happened

d6-run10 stopped at iteration 9 of 20. Not the power outage: the driver
crashed on its own at ~23:30 (clean traceback + its own CRASHED notify),
and the outage came later. Iterations 0–8 completed and are clean
(arms at iter-4: 0.520 ± 0.025; KL/entropy/veto all quiet; tripwire
0–1/iteration = the known bf16 tail).

## The cascade (three layers, each real)

1. **Two drill completions wedged in a targeting loop** ("Spider-Man
   2099 — Couldn't add to stack, failed to target", repeating) and each
   wrote ~1 GiB of raw obs before RAW_CAP truncated the frame — the
   runaway guard did its job frame-side. New engine-hang class for the
   worklist (wedge, not crash; distinct from the two D2 crash classes).
2. **The wall-clock cost of the wedges hard-capped game 734, and the
   hard-cap ABANDONS the game thread** (TimeLimitedCodeBlock) — but
   completions run ON the game thread, and the fork-frame statics had
   no stale-thread binding (the mainline has `currentGame`; forks had
   nothing). The abandoned, interrupt-flagged thread's
   `getChannel().position()` closed the shared fork-file fd —
   `Stream Closed` forever after, and every subsequent "frame" became a
   clen-0 phantom idx row (zstd buffered ~130 KB raw per frame and only
   touches the file at close, so writes "succeeded" into a dead fd).
3. **`ingest --forks` decoded frames inline with no bad-frame path** —
   one undecodable frame raised, `check=True` killed the driver.

## Fixes (fork `7249a41b60`, Anvil `eb6381f`)

- **Java stale-thread guards:** `forkCurrentGame` owner binding on all
  fork-frame writes (dec/ret/end); `startForkGame` falls back to
  wire-only when the parent's mainline session is already closed (an
  abandoned thread can never touch the frame file; under
  `--drill-sample` its g=−1 header makes the server refuse, so nothing
  trains); `RolloutMonitor` refuses to fork from a game already
  declared over. Fork suite 294 green; jar rebuilt.
- **Python quarantine:** forks ingest drops undecodable / phantom
  (clen 0) / runaway (rlen > 1 GiB) frames loudly — no outcome row,
  dropped from the index, listed in `manifest.drill.quarantined`. One
  bad frame now costs one frame. Fixture test; suite 115 green.

## Resume

Same launch command: iterations 0–8 skip via loop_state, iteration 9's
full-game stores reuse (they had ingested before the crash), the drill
phase re-runs from scratch on the fixed jar (stores.json was never
written — phase idempotency doing its job). Watcher + waiter re-armed.
The corrupt drillmix009 run dir stays orphaned on disk as the incident
record; the driver's before/after glob excludes it.

## Notes

- The failure hit at iteration 9 of 9 drill phases ⇒ expect this class
  roughly per-run without the fixes; with them, the worst case is a few
  quarantined completions per wedge event.
- Per-completion wall-clock budgeting (a wedged completion can eat the
  parent game's hard-cap) noted as a possible refinement — the
  ROLLOUT_TIMEOUT + RAW_CAP + quarantine now bound the damage, so not
  scheduled.
