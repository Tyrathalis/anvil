## The two open decisions, resolved

- **Where the helper lives: `forge-gui`, shared.** A static pure-geometry
  class (`forge.util.RotatedRect`: `contains` + `boundingBox`) with zero
  libGDX/Swing imports. That dissolved the "add test infra to
  forge-gui-mobile?" question — the test (`RotatedRectTest`, 5 TestNG
  methods) sits in `forge-gui-desktop`'s existing tree, which already depends
  on `forge-gui`. Desktop's own hit-test round later reuses the same class.
- **Angle convention:** the helper speaks mobile's `startRotateTransform`
  convention (stock tap = −90); Swing callers will pass the negated
  `Graphics2D.rotate` angle in degrees — which is *also* −90 for stock tap,
  so the conventions coincide exactly where it matters.

## The identity gate, run honestly

- Hit-test: **bit-identical to the legacy swap box at −90 over ~60M grid
  points** (4 geometries including awkward floats, zero mismatches). Trig is
  snapped exactly at multiples of 90 to make that achievable.
- Bounding box (feeds only the arrow anchor): identical to ~1e-5 — the noise
  floor is call-site float pivot rounding, measured by the test's first
  failure (`2.0000038` vs `2.0` under a `delta=0` assert) and then asserted
  at `1e-4` *with the reason written down*. The strict claim stays on the
  hit-test, where a flipped comparison could matter.
- Arbitrary angles are checked against a double-precision forward-transform
  oracle (inside/outside lattices with a boundary band excluded), so the
  helper is already known-correct for the future configurable angle, not
  just at ±90.

## The derivation found a real bug before any angle became configurable

Working out the composed transform for **180-rotated fields** (local
two-human non-hotseat matches — precisely the Commander-night mode) showed
the current hit-box is provably misaligned: `CardAreaPanel.draw` wraps cards
in an outer 180° rotation about the untapped rect center and flips
`getTappedAngle()` to +90, but the angle-blind hit-test kept the −90 swap
box. Net: **the drawn tapped card sits offset by h−w from where taps are
accepted** — the top ~40% of the drawn card misses, and a band of empty
space below it hits. Input coordinates never see draw transforms, so nothing
downstream compensates.

Fix: `CardAreaPanel.renderedCardContains` undoes the outer 180 (a point
reflection about the center — identity for untapped cards) before the base
test; targeting arrows had the same offset and now anchor to the drawn box.
This is a *deliberate* behavior change in that mode, documented as such in
the commits; the default orientation is covered by the bit-identity gate.
