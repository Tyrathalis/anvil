# 2026-08-22

Playable-fork track. Custom deck sleeves, from a question to a shipped feature on
both clients, including sharing between players. Research track untouched.

## Done

- **Design round before code.** The ask was "can we add custom sleeves"; the answer
  turned out to be that upstream already ships *card-art* sleeves (three June commits
  by MostCromulent, in our v16 sync), and the missing piece was only *your own image*.
  The architecture followed from that: a custom sleeve is just another key in the
  existing sleeve-art pipeline, so deck-header persistence, the lobby wire, `PlayerView`
  and both renderers needed no changes — only key-to-file resolution did.
- **Sharing designed away from URLs.** A URL field would make every client fetch from a
  host another player chose, handing that player each viewer's address, and would not
  even deliver "everyone sees the same sleeve" (a server can vary bytes per requester).
  Peers exchange validated bytes in-band, named by SHA-256. Riding the existing transport
  also means whatever secures that connection secures this — the reason not to give
  sleeves a side channel. Standing note for a future TLS round: `SslHandler` at the head
  of both pipelines is ~10 lines; the hard part is identity, and a WireGuard/Tailscale
  tunnel buys the whole trust gap for zero code.
- **Built in stages, each committed green:** `CustomSleeves` (validation + content-addressed
  identity, forge-core) → `SleeveStore` (hash-named storage, bounded import) → desktop Swing
  picker → libgdx render/import/picker → `SleeveExchange` → the wire.
- **Guards.** 256 KiB sleeve cap, PNG/JPEG magic-byte allowlist, header-read dimensions
  before any raster allocates, 16 MB / 50 MP source budget, hex-only key chokepoint,
  per-seat rate limit, session-scoped borrowed sleeves cleared at startup, reachable
  opt-out. Every guard was watched to fail before being counted.
- **Sharing verified across two real processes** (`SleeveShareDriver`, separate `user.home`
  each): honest run landed a byte-identical copy in the host's session dir while the host's
  own library did not exist; tamper run (one sleeve's name, another's bytes) refused with
  "the image does not match the sleeve it claims to be", nothing written.
- **Three releases published** (jar + APK, both verified through the production code path:
  manifest re-parsed by the shipped jar, res delta resolving at the pushed commit, APK dex
  containing the new classes).

## Broke / surprised me

- **Built the picker on the wrong client first.** I assumed "desktop" meant `forge-gui-desktop`
  (Swing) and built the whole picker there. The playable release ships `forge-gui-mobile-dev`.
  I only discovered this at the point of launching it for playtest, by reading
  `release-playable.sh`. The shared core was client-agnostic so nothing was wasted, but a
  glance at the release script *before* choosing where to put UI would have cost thirty
  seconds. **Rule: check which artifact ships before building a surface for it.**
- **Two security tests did not bite.** The traversal test asserted `fileFor("s:../../etc/passwd")`
  was null — and passed with the chokepoint removed, because the target did not exist. The
  byte-cap test was fully masked by the Content-Length pre-check, so the streaming read loop
  never ran. Both only surfaced by mutating the guards and watching the suite stay green.
  The hardening round's discipline paid for itself the first time it was applied.
- **`mvn -Dtest='A+B'` matches nothing**, and with `-Dsurefire.failIfNoSpecifiedTests=false`
  that is `BUILD SUCCESS` with zero tests run. One "green" build was vacuous. Separator is a
  comma.
- **The file and link import paths disagreed** — found in play, not by tests: a picked file
  downscaled happily while the same image behind a link was refused as "too large", because
  `download()` applied the *sleeve* cap to the *source*. Reconciling them onto one shared
  `probeSource` also closed a decompression-bomb hole present on **both** paths.
- **A stale note in this repo produced a wrong claim.** CLAUDE.md still said Android
  build-tools 35 / platform 35 were "not on the box"; they have been installed for a while,
  and an APK built that same morning was sitting in the release proving it. Corrected at the
  source. **A stale status line is not inert — it gets believed.**
- **46 MB of the published jar was garbage.** Chasing a 2.7 MB size change found
  `target/classes/target/classes/…` nested 48 deep — 610 files, 46.4 MB of 106.6 MB. The
  mobile-dev pom copies resources from `${project.basedir}` with `**/…png` globs, and
  `target/` is under basedir, so every build re-copies the previous build's copies one level
  deeper. Excluding `target/**` takes the jar to 60.3 MB. This is stock upstream config:
  every Forge mobile-dev jar built more than once carries it.
