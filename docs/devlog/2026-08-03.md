## RETRACTION (same day, afternoon): there was no environment regression

The morning section above asserts a ~37% environment regression. **It was
a benchmark-configuration artifact of my own.** The elimination chain that
found it: LTS kernel boot (708.7 — "still slow"), jemalloc preload (726.7),
`--calibrated` no-renice (736.6), ananicy stopped (717.1), GCC runtime
r346 downgrade (703.0) — five more suspects "at the floor" with suspicious
consistency — then the cross-check that broke the story: **the training
runs' own gen_s never regressed across the 07-26 boundary** (run7b median
943 g/h blended pre-update; run9 1060 post-update). The artifact: my
single-arm invocations sized chunk = games/workers = exactly ONE round —
no refill, so elapsed = the slowest worker's contiguous deck-pair block.
Worker-finish spread in a chunk-30 run: [0, 28, 32, 35, 66, 80, 163, 450,
741]s — an 11× tail; the box spent the last ~12 minutes on one worker
(user's fan observation corroborated: quiet fans = thinning pool). The
07-26 "fast" bench ran chunk 15 (two rounds). Reproducing that exact
config on the CURRENT environment: **w=8 1272.6 g/h, w=16 1508.0** — the
box is ~10% FASTER than the fast era. All downgrades restored (kernel
7.1.6, gcc r595, ananicy on); **reference sweep on the restored standard
config: w=8 1280.1 g/h / w=16 1477.1 g/h** — within a few % of the
downgraded-config numbers, closing the case: environment differences were
worth ~nothing, chunking was everything. (The w=16 figure is still the
1-round-at-chunk-15 shape — tail-suppressed, so true w=16 is likely
higher; the next sweep at `--games 320` chunk 10 firms it up.)

What survives the retraction: the serve-path profile (0.05 ms
Python-active/request — measured within games, chunking-independent), the
disk exoneration (1% NVMe util under full load; the early-project SSD
concern is retired), the noise-floor discipline (it caught the
inconsistency), and the incident fixes (orphan worker, watcher lessons).
**What it OVERTURNS beyond the regression: the standing "w=16 is 6%
slower, ~189 rps ceiling" conclusion was partly the same artifact** (at
chunk 15, w=16 got exactly one round on 07-26 too). w=16 now measures
+18% over w=8 — a REAL D4 lever candidate: the training loop at w=16
with chunk ~15 (480 games → 32 chunks = 2 rounds) is potentially +30-40%
generation throughput, to be validated end-to-end in a mini-run.

`bench_generation.py` hardened: auto chunk-sizing guarantees ≥2 rounds
per arm, explicit `--chunk` refuses tail-bound configs, hazard documented
in the docstring. Standing lesson: cross-era throughput comparisons are
valid ONLY at identical chunking; a "stable" wrong number (CV 1.26%!) is
stable because same seeds → same slowest chunk.
