## Broke / surprised me

- **Forced-draw "winner" is garbage by construction**: `setGameOver(Draw)`
  runs `Player.onGameOver`, which marks EVERY surviving player as won;
  `GameOutcome.getWinningLobbyPlayer` then returns an arbitrary
  map-order pick — JVM-varying, so the smoke's determinism diff caught
  it (33/72 rows differed ONLY on `winner`, identical snapshots). Sched
  rows now extract a unique per-player winner (`nWon != 1 ⇒ -1`).
  Latent same wart in `CensusRun.certRow` and the seq-probe rows —
  harmless historically because the certify standard's unended-roll
  guard (payment_ceiling.py gates on `ended` for both pair rows)
  excluded exactly those rows from every M9 read.
- **rollSeed must key on the target turn, not the fork counter**: stage 2
  re-runs the positive SUBSET, so fp numbering shifts between stages and
  the fp-keyed derivation would have silently broken the spec's
  rollSeed-identity both-horizon trick. Caught in self-review before any
  data; keyed on (game seed, target turn, roll) now.
- Random-legal (local-oneshot) play realizes mostly mana abilities and
  lands; real multi-cast turns are ~1 per 4 games — the smoke mines 12
  games for 3 points. Fine for mechanics; the model-serve smoke rides
  the fresh census.
- **The serve smoke's first pass OOM-killed its JVM** — and the cause is
  a retention leak worth remembering: cancelled rollout watchdog clocks
  sit in the ScheduledThreadPoolExecutor queue until their 120s
  deadline, each lambda pinning its whole Game copy. Invisible at
  seq-probe scale (3 arms × K); fatal at sched scale (33 arms × 8 rolls
  = 264 copies per point). Fixed with remove-on-cancel at the pool
  (fork `07900c3db1`), proven trace-invisible empirically.
- **…and then ALL EIGHT first-launch sweep lanes OOM'd anyway — the real
  leak is upstream: `forge.ai.AiCache.dataMap`** (into the small hours,
  2026-08-26). Diagnosis chain worth keeping: forced full GC left 121
  Games live at 119 completions (true leak, 1:1); referrer histograms
  only showed each game's internal structure; ptrace blocked jhsdb; so
  a 4.9GB heap dump + a hand-rolled hprof forward-BFS from class
  statics (weak-referent edges excluded) named the root in one pass —
  **144/146 retained Games rooted at `AiCache.dataMap`**. The mechanism:
  Forge clears this global AI memo at the top of every heuristic
  `AiController.chooseSpellAbilityToPlay`, but BRIDGED seats never take
  that path, while payment/canPlaySa keep populating it — so every
  bridged JVM since M1 has leaked one game graph per game, silently
  masked by harness chunk recycling. Single-JVM sweep lanes exposed it.
  Fix (fork `7716bbe44d`): `AiCache.clear()` between completions and
  between mainline games — outside any game's play, so census replay
  parity holds; proven trace-invisible (536/536 serve-smoke rows
  identical across the fix, re-run determinism re-verified). Upstream
  note: AiCache's own TODO admits the missing scoping — an
  upstream-candidate (bounded/game-scoped cache) queued.
- One launch stumble worth the checklist: a `cd` persisting in the
  relaunch chain pointed the wrapper's log redirection at a relative
  path — the launch silently no-op'd. Absolute paths in every detached
  launch line, always.
- The Chronicle side stream leaks into the research jar's logs: the
  shared Forge user prefs carry `CHRONICLE_BINDER` (a playable-fork
  ItemManagerConfig), which prints an IllegalArgumentException stack at
  every FModel init. Harmless noise (present in every successful run
  today) — but it cost minutes during the lane-failure diagnosis by
  masquerading as the fatal error. The shared-user-dir hazard class
  again; watch-list note added.
- The parity check surfaced a second face of the both-win wart:
  MAINLINE games that hit the 300s draw clock report status "won" with
  an arbitrary winner in games.jsonl (`getWinningLobbyPlayer` again —
  ~1/20 games at census pace). Pre-existing and identical on the bundle
  jar, and harmless to the ceiling instrument (sampling consumes obs
  turn-groups, not winners) — but any read that trusts mainline census
  winners should gate on `draw_clock`/wall-time first. Not fixed
  in-jar this session (mainline winner extraction is shared with
  long-standing results consumers; touching it mid-census would be a
  boundary question — flagged for the M10 label work instead).
