A short planning session on the side track: what a human-facing build needs
before Commander night. No code changed in the fork.

## Done

- **Item 4 (Adventure window resizing) diagnosed** — the worklist said "not yet
  diagnosed"; it is now, and the first finding is that it is **not our bug**.
  `forge-gui-mobile-dev/src/forge/app/GameLauncher.java` is byte-identical
  between our pinned base (`3e3818f1ba`) and upstream, and upstream's tip
  touches the file only for an unrelated window-focus refactor. Stock upstream
  behavior ⇒ upstream-PR candidate, which is the pattern the fork already
  follows.

  Three layers, and the first one is the whole headline:

  1. `config.setResizable(false)` (`:118`) makes GLFW publish fixed min=max
     size hints, and KWin/GNOME refuse to tile a window that advertises fixed
     size hints. **That single line explains the missing corner snapping** — the
     compositor never even offers the tile. Nothing about Forge's layout code
     is implicated.
  2. `Forge.screenWidth/screenHeight` are captured once at init (`Forge.java:206`,
     with a comment saying they only change on restart) but read *every frame*
     in `render()`; `resize()` forwards the new size to the screen and scene but
     never updates the statics. Flip layer 1 alone and you get a window that
     resizes around a stale viewport.
  3. `Utils.HEIGHT_RATIO` is `static final` (`Utils.java:12`), so `Utils.scale()`
     — fonts, `FCardPanel.PADDING`, finger metrics — is frozen at launch scale.

  Planned as tiers T1/T2/T3 so the snapping unlock (T1: resizable + live
  viewport) ships without pre-paying for the T2 audit of every `static final`
  that transitively reads `Utils.scale()` at class-init.

- **Item 5 added: shallower configurable tap angle**, both clients (user picked
  "too steep, want a shallower tilt" and "plan for both"). The angle is one line
  per client — `FCardPanel.getTappedAngle():70` returns `-90`,
  `CardPanel.TAPPED_ANGLE:89` is `Math.PI/2`. The actual work is that **three
  geometry consumers hard-assume exactly 90°**: mobile
  `renderedCardContains:74` and `getTargetingArrowOrigin:560`, desktop
  `PlayArea.getCardPanel:718`. All three swap width/height rather than rotating,
  so at any other angle they fail *silently* — the card renders where you cannot
  click it, which is the worst possible failure mode for a UI nicety.

  The plan therefore lands the hit-test generalization **first, at an unchanged
  90°**, where pixel-identity is the refactor's own correctness gate. Nice
  accident: `CardPanel:647` already inverse-rotates the mouse point into card
  space for its badge hit-test, so the technique is in-tree to copy rather than
  invent — and step 1 is upstreamable alone as a latent-correctness fix,
  separable from the opinionated preference.

- **Branch-hygiene rule written down.** Another workstream shares the `playable`
  branch family. Our items touch UI files only and overlap it nowhere, but a
  branch lives in exactly one worktree — claiming `playable` would block the
  other stream. Rule:
  `git worktree add -b playable-qol ../forge-play playable`, which reads the tip
  without claiming the branch.

- Worklist resequenced into two tracks (QoL 4→5, updater 3→2→1) with the QoL
  track first: it is what Commander night actually feels; the updater track only
  matters once we are shipping builds to other people's machines. Project-map
  card swept in the same commit.

## Decisions taken after the writeup (same session, user)

- **Overlap over repack** for the tap-angle layout reservation: keep the 90°
  box, let shallow-tilted cards overhang their neighbours. It is the table look
  and it is also the cheap option (no row-packing changes, no repack cascade).
  Added a consequence to the acceptance criteria that wasn't obvious when the
  option was framed: overlap makes *draw order* visually load-bearing for the
  first time — an overhanging card must be drawn under its right-hand
  neighbour, or the effect reads as clipping.

- **Mobile/Adventure first, both clients eventually.** The user asked whether
  supporting only one interface would be dramatically easier, and expected
  mobile to be the cheap one. Measured instead of assumed, and the answer
  inverts: **desktop is the cheaper client** — one exact-90 hit-test vs mobile's
  two, an animation path that already scales off the constant vs mobile's
  hardcoded `-90`, an inverse-rotation helper already in tree, one settings
  screen vs two. Mobile is ~2× desktop, not 10×, and the shared costs (value
  list, helper, localization, actually playing a game) are paid once either way.
  So the split isn't worth a split experience. Mobile still goes first, on
  narrower grounds: item 4 is mobile-only, so it's the tree already being built
  and played on.

  Also checked the premise that the project is moving toward the mobile UI —
  directionally true, weaker than stated: 12-month upstream commits are 430
  (`forge-gui-mobile`) vs 262 (`forge-gui-desktop`). Desktop is the
  slower-moving of two live UIs, not a dead one, and the plan says so
  explicitly so nobody later reads "mobile-first" as "desktop is abandoned".

- **Friends won't need to pin a version.** Falls out of the default-`"90"`
  design: the angle is a local render preference that never crosses the wire, so
  a table can mix clients and angles freely.

- **`playable-qol` created** (`cc32912078`, worktree `../forge-play`) — verified
  `playable` is still unclaimed by any worktree afterwards. Anvil-side docs stay
  on `main`: they're the public record of the track and collide with nothing;
  only the code needed its own branch.

- Kept my discrete value list over the entry's suggested free-form precedent:
  `UI_ACTIONABLE_HIGHLIGHT_COLOR` is right for *validation* (parse → fall back
  to `getDefault()`) but needed a bespoke widget class on mobile, where a short

**Deck-site sync graduated into the track** (user) as items 6 and 7, and the
sequence became 4 → 6 → 5 → 7.

The user proposed folder syncing — "including syncing all public decks from a
particular user — that avoids any need for auth". Checked it rather than
agreeing, and the two halves come apart:

- **Public-decks-by-owner is genuinely auth-free and is the right primitive.**
  Archidekt serves `/api/decks/cards/?owner=<name>&ownerexact=true` unauthenticated
  and paginated. Caveat recorded: no API docs at all (open beta, changes too
  often to document) and explicit rate limiters, so parse tolerantly.
- **Folders do the opposite of what was hoped.** No public folders endpoint
  surfaced, and folders are *per-user organization* — the thing that lives
  behind an account. Folder sync would **reintroduce** auth, not dodge it. The
  auth-free property comes from decks being public, not from folders. The
  organizing goal survives without any folders API: sync into a *local* Forge
  folder per username, and check whether the listing payload already carries a
  category/tag for free client-side filtering.
- **Moxfield bulk deferred to a stub**: gated behind a support-issued
  whitelisted User-Agent plus Cloudflare, with a documented Nov-2025 issue where
  whitelisted agents still hit reCAPTCHA. Relationship problem, not an
  engineering one; it must not gate the feature.

Item 6 (mobile exposure) turned out better than the upstream note implied:
`DeckUrlLoader` and both providers already live in the **shared** `forge-gui`
module, and `FDeckChooser` (desktop) is their *only* consumer. Mobile isn't
missing a port, just a button — which makes it the best value-per-line item on
the list and puts it second in the sequence, ahead of the tap angle.

## Sync storage layout — both halves answered from existing code

User proposed a user-folder per format, plus a category for decks that match no
format and aren't labelled. Checked both against the code rather than reasoning
from taste, and both answers came out of it.

**Format folders: recommended against, with a caveat.** Imported decks already
live in their own flat store (`DeckUrlLoader.getStorage():150` → `decks/URL/`),
not Forge's format-partitioned stores — so the layout was never constrained;
it's free. Against adding a format level: the axis already exists twice in the
UI (`FDeckChooser` is constructed per `GameType` at `:75` and drives layout off
`getDeckFormat()`; the URL pool goes into an `ItemManager` with its own filters
at `:302`), and on a Commander night a format level degenerates into chains of
single-child folders. Bigger reason: **re-sync must never move a deck** — any
"flat until multi-format, then split" rule relocates existing decks the first
time a friend uploads a Modern list. Caveat recorded rather than glossed: that
reasoning is measured on the *desktop* chooser, and mobile is the priority
client, so it gets re-checked after item 6 exists.

**The invalid-deck bucket has a prerequisite that is invisible from outside the
code, and it's the good find of the session:** there is no unknown-format state
today. Both providers already collapse unknown to `Constructed` *silently* —
Archidekt maps four numeric cases and defaults the rest
(`ArchidektDeckUrlProvider:127-137`), Moxfield calls
`smartValueOf(value, Constructed)` and catches the exception to return
`Constructed` anyway (`DeckUrlLoader:142-148`). So an Oathbreaker list or an
unlabelled deck is *already* filed as Constructed and is indistinguishable from
a real one. The bucket the user asked for cannot be built until the raw site
label stops being destroyed at the provider boundary.

Then the word "invalid" turned out to cover three different things, only one of
which is a routing problem: unmapped format (route it), deck doesn't conform
(`getDeckConformanceProblem()` already returns a reason — annotate), cards Forge
can't resolve (annotate). Recommended `Unsorted` over `Invalid` for the one
bucket that survives — in that case the deck is fine, we just couldn't place it,
and a blaming name sends people hunting for a defect that isn't there. And (b)
and (c) must never move a deck: it's still your friend's deck, and one that
becomes legal later would have to move back.

## Closed out

- **The picker-filtering question closed the same session**, by the user knowing
  the engine better than the code search did: Forge runs its own legality check
  when a deck is taken into a game — `FPref.ENFORCE_DECK_LEGALITY`
  (`ForgePreferences.java:205`, default `"true"`), consumed at
  `GameLobby.java` and shared by both clients. So the picker only routes and
  labels; conformance has an authoritative, default-on gate downstream. It also
  retroactively strengthens the "annotate, don't move" rule — quarantining
  non-conforming decks would duplicate a check Forge already performs at the
  only moment it matters.
- **Ordering agreed** (4 T1 → 6 → 5 step 1 → 7, updater track 3 → 2 → 1 behind
  it), and the track finally has a horizon: Commander night ran today, so the
  next is ~1–2 weeks out. Comfortable for the sequence in order — the worry
  about pulling items 1–2 forward doesn't apply at that distance. Worth noting
  those two are the items the user has now independently hit in real play twice,
  which is a better prioritization signal than anything I derived from the code.
