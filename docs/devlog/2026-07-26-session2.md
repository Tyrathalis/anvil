# 2026-07-26 (session 2) — the playable fork's QoL track, planned

A short planning session on the side track: what a human-facing build needs
before Commander night, written up while a parallel workstream holds the
`playable` branch family. No code changed in the fork.

## Done

- **Item 4 (Adventure window resizing) diagnosed** — the worklist said "not yet
  diagnosed"; it is now, and the first finding is that it is **not our bug**.
  `forge-gui-mobile-dev/src/forge/app/GameLauncher.java` is byte-identical
  between our pinned base (`3e3818f1ba`) and upstream, and upstream's tip
  touches the file only for an unrelated window-focus refactor. Stock upstream
  behavior ⇒ upstream-PR candidate, which is the pattern the fork already
  follows.

  Three layers, and the first one is the whole headline:

  1. `config.setResizable(false)` (`:118`) makes GLFW publish fixed min=max
     size hints, and KWin/GNOME refuse to tile a window that advertises fixed
     size hints. **That single line explains the missing corner snapping** — the
     compositor never even offers the tile. Nothing about Forge's layout code
     is implicated.
  2. `Forge.screenWidth/screenHeight` are captured once at init (`Forge.java:206`,
     with a comment saying they only change on restart) but read *every frame*
     in `render()`; `resize()` forwards the new size to the screen and scene but
     never updates the statics. Flip layer 1 alone and you get a window that
     resizes around a stale viewport.
  3. `Utils.HEIGHT_RATIO` is `static final` (`Utils.java:12`), so `Utils.scale()`
     — fonts, `FCardPanel.PADDING`, finger metrics — is frozen at launch scale.

  Planned as tiers T1/T2/T3 so the snapping unlock (T1: resizable + live
  viewport) ships without pre-paying for the T2 audit of every `static final`
  that transitively reads `Utils.scale()` at class-init.

- **Item 5 added: shallower configurable tap angle**, both clients (user picked
  "too steep, want a shallower tilt" and "plan for both"). The angle is one line
  per client — `FCardPanel.getTappedAngle():70` returns `-90`,
  `CardPanel.TAPPED_ANGLE:89` is `Math.PI/2`. The actual work is that **three
  geometry consumers hard-assume exactly 90°**: mobile
  `renderedCardContains:74` and `getTargetingArrowOrigin:560`, desktop
  `PlayArea.getCardPanel:718`. All three swap width/height rather than rotating,
  so at any other angle they fail *silently* — the card renders where you cannot
  click it, which is the worst possible failure mode for a UI nicety.

  The plan therefore lands the hit-test generalization **first, at an unchanged
  90°**, where pixel-identity is the refactor's own correctness gate. Nice
  accident: `CardPanel:647` already inverse-rotates the mouse point into card
  space for its badge hit-test, so the technique is in-tree to copy rather than
  invent — and step 1 is upstreamable alone as a latent-correctness fix,
  separable from the opinionated preference.

- **Branch-hygiene rule written down.** A parallel workstream is landing commits
  on the `playable` branch family. Our items touch UI files only and overlap it
  nowhere, but a branch lives in exactly one worktree — claiming `playable`
  would block the other stream from committing to it. Rule:
  `git worktree add -b playable-qol ../forge-play playable`, which reads the tip
  without claiming the branch.

- Worklist resequenced into two tracks (QoL 4→5, updater 3→2→1) with the QoL
  track first: it is what Commander night actually feels; the updater track only
  matters once we are shipping builds to other people's machines. Project-map
  card swept in the same commit.

## Broke / surprised me

- **I nearly leaked the other workstream's shape into a public repo.** First
  draft of the branch-hygiene section named the branch, its upstream base
  commit, the commit count, and characterized the changed area. The Anvil repo
  has been public since 07-12, and the worklist's own footer says that note is
  *deliberately* held back pending private upstream disclosure. The existence
  was already public; the specifics would have been a pointer for someone
  hunting. Rewrote it to carry only the coordination rule. Lesson worth keeping:
  when writing into this repo, "is this file public?" is a question to ask
  *before* drafting, not at review — I caught it on reread, which is one draft
  too late.

- The tap angle looked like a one-line taste change and is not. The silent
  failure mode (draw and hit-test disagreeing) is exactly the kind of thing that
  ships fine in a smoke test and annoys someone in game three.

- `CardUnTapAnimation.drawCard:288` hardcodes `-90 + (percentage * 90)` instead
  of delegating to `getTappedAngle()` — harmless today, a real bug the moment
  the angle is configurable, and worth fixing on its own regardless.
