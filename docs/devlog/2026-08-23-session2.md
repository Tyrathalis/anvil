# 2026-08-23 (session 2) — D6 in play: four bug rounds, and the one where I started looking

Chronicle track, continuing [2026-08-22-session3](2026-08-22-session3.md) (D5
opened, D6 designed, built and published as v17). This session is what happened
when a real person used it. Four rounds of defects, v18 through v22, and the
honest arc is that the first three were shipped without my having seen the
screen and the fourth was found in ninety seconds once I did.

**D6 is now verified in play** — the author has built decks and played rival
games on the phone.

## Done

- **The tear was backwards.** The grip term put the first peel at the edge the
  finger travelled *towards*, so a rightward swipe tore from the right edge
  leftwards. You grab the near edge and pull across, so the tear front should
  travel WITH your hand. One inverted sign (`2177e66f6d`). Verified later by
  capturing a mid-drag frame: swiping right, the left columns let go first and
  the split staircases away rightwards.
- **The deck editor crashed on open.** `ItemManagerConfig.QUEST_EDITOR_POOL`
  sorts on `ColumnDef.NEW`, and NEW ships with null sort/display functions —
  "functions will be set later" — so `ItemColumn`'s constructor throws
  *"A sort function hasn't been set for column New"* before a card is drawn.
  Quest and Adventure both supply them via `getColOverrides`; I reused Quest's
  config without reusing Quest's contract. Fixed with a thin `FDeckEditor`
  subclass, supplying the column rather than dodging it — in a collection game
  the cards you just pulled are the ones you want while building (`1cf95bf9e5`).
- **Pile-by could still take the app down.** `ImageView`'s pile-by read
  `ColumnDef`'s raw `fnSort` instead of the caller's override map, so piling by
  NEW/PRICE/OWNED/DECKS dereferenced null mid-layout. Fixed generically, and it
  is not Chronicle-specific — Quest's editor pool and inventory can both reach
  it, so it went on the upstream-candidate queue (`fa6429d5e8`).
- **Chronicle stopped borrowing Quest's editor settings.** `ItemManagerConfig`
  holds *persisted* per-config view state (group-by, pile-by, view index), so
  sharing `QUEST_EDITOR_POOL` meant Chronicle and Quest silently reconfigured
  each other and a bad value written by either broke the other. Chronicle now
  has `CHRONICLE_DECK_POOL`, the way its binder already had `CHRONICLE_BINDER`,
  carrying OWNED as well as NEW.
- **THE ROOT CAUSE of the empty catalog** (`ef6a789a37`): `IDeckController.setEditor`
  has two halves — store the editor, and push the controller's model into it.
  `FileDeckController` does both, the second via `editor.notifyNewControllerModel()`,
  which is what populates `FDeckEditor`'s own `deck` field. **My controller only
  did the first.** So `getDeck()` returned null through construction,
  `CardManagerPage.initialize()`'s `if (getDeck() != null) onDeckChanged(...)`
  never fired, `needRefreshWhenShown` was never set, and `CatalogPage.refresh()`
  never ran. The catalog kept the empty pool it was born with, permanently, and
  the search ratio read `(0 / 0)` because the pool genuinely held nothing.
- **The rival roster ships with the code now** (`320ddc144f`). A pre-D6 save
  showed no rivals on device. Delivery logic checked out — `rivals.txt` is in
  `assets.zip` and the manifest, and `DeltaManifest.diffAgainst` does include
  files the client lacks (verified against the published manifest with a
  resolver reporting everything absent). The file simply had not reached that
  install: **every other Chronicle data file was present from the original
  assets.zip, and rivals.txt was the only one introduced after it.** The durable
  fix is not more reliable delivery but no dependence on it — the roster now
  also rides in the jar/APK as a classpath resource, with res/ still winning
  when present so the file stays moddable.
- **Pool construction moved into the headless controller**
  (`ChronicleController.collectionAsPool()`), because "what can I build from?"
  was sitting in a screen where no test could reach it. Now asserted headlessly:
  the catalog holds every copy the collection holds, and it is a copy.
- Suite 520 green (71 Chronicle). Published v18–v22, post-publish routine each
  time. Shared-file footprint went from zero to three files — an enum entry, a
  column set, and the pile-by fix, all additive or generic.

## Broke / surprised me

- **Three rounds of confident wrong diagnoses, and the pattern behind them.**
  Each round I found a *real* mechanism, fixed it, and treated a confirmed
  mechanism as a complete explanation. The crash and the freeze were both real
  and are both fixed; neither was the empty catalog. Reading source told me what
  *should* happen and I kept believing it over the symptom.
- **What broke the deadlock was one line of measured state.** A file-writing
  probe in `CatalogPage.initialize()` printed `needRefresh=false visible=true`
  and the answer was immediate. I had reasoned my way to exactly the right
  hypothesis two rounds earlier ("the page never refreshes") and then talked
  myself *out* of it by mis-reasoning about `isVisible()`.
- **My probes printed nothing at first, and that nearly cost another round.**
  Forge redirects stdout/stderr after boot, so `System.err.println` went
  nowhere — and its own `forge.log` also stops at boot. Absence of probe output
  was not absence of execution. Writing directly to a file with
  `Files.write(..., APPEND)` was the fix.
- **The compositor screenshot can't see the app.** On this Wayland session the
  LWJGL window is an XWayland client that never appears in a screen capture,
  though the WM reports it focused. `import -window <id>` (ImageMagick) captures
  it perfectly and `xdotool` drives it. That pair — plus an isolated
  `-Duser.home` — is the whole harness, and it is the most reusable thing this
  session produced.
- **I launched stock Forge against the real profile by accident.**
  `open_application "Forge Desktop"` started the *installed* Forge rather than
  focusing the test build. Killed within seconds; `~/.forge/decks` untouched
  (the tree `launch --pool` hashes), but `forge.preferences` got rewritten with
  its own values. Use the window title, never the app name, for a build under
  test.
- **A test can break its neighbours.** My first regression test for the NEW
  column blew up in `ItemManagerConfig`'s static initializer and took four other
  Chronicle test classes down with it. It needs `AITest` so the model is up.
- **`GameRules` inherits the global `UI_ANTE` preference** — noted at build time
  last session, worth repeating because it would have silently gambled the
  player's collection, permanently, in a mode whose entire loop is accumulation.

## Standing lessons

1. **A libGDX screen defect cannot be found by reading, and cannot be tested
   from the desktop tree.** Drive the build. The harness is: isolated
   `-Duser.home`, `xdotool` for input, `import -window` for capture.
2. **Probe by writing to a file.** Forge's own logging stops at boot, so console
   probes are worse than useless — they are misleading.
3. **A confirmed mechanism is not a complete explanation.** Check whether it
   accounts for *every* reported symptom before shipping it as the fix.
4. **Small curated data that ships with a feature also ships inside the
   jar/APK.** res/ arrives by asset delta and can lag the code that needs it, or
   never arrive on an install whose delta has not run. res/ wins when present;
   the bundled copy guarantees the feature exists. A test pins the two copies
   byte-identical.
5. **Implementing an interface means implementing its contract, not its
   signature.** `setEditor` compiles fine doing half the job.
