# 2026-08-06 session 2 (playable track: whose-action tracking)

## Done

- **Diagnosed the game-night "waiting on the wrong player" bug to its root.**
  Both the avatar priority ring and the bottom-bar "Waiting for X" text key on
  `HasPriority`, which `PhaseHandler` writes exactly once at the END of each
  main-loop step (`PhaseHandler.java:1157`) — after the input wait, stack
  resolution, and phase advance. Consequences: declare attackers/blockers run
  inside `onPhaseBegin` with flags pointing at the previous holder (blockers
  wait displayed "Waiting for [attacker]"); resolution-time choices same;
  `GameEventPlayerPriority` fires *before* the flag write, so the net delta
  flush riding it always carried one-step-stale flags; and
  `updateWaitingDisplay` re-rendered a name captured once at await time, so
  handoffs never updated the text — exactly the user-reported experience.
  All of this is stock upstream code (PRs #9671/#10555), not fork work.
- **Built the fix at the source (`e9e0830993` on `playable`, pushed).** New
  `AwaitingInput` trackable stamped by `InputQueue` when the game actually
  blocks on a player's input (set on `setInput`, cleared when the queue
  empties — safe off the game thread because the game thread is parked on the
  input latch during `removeInput`). `GameEventAwaitingInput` fires after the
  stamp, and the new `IGuiGame.flushGameView` (no-op locally; in
  `RemoteClientGuiGame` a game-thread delta flush over the existing
  `setGameView` wire method — no protocol change, `forge.` prefix already
  passes the hardening wire filter) delivers the flag to every client while
  the wait is live. Prompt side: `findWaitingForPlayerName` prefers the new
  flag, the waiting timer recomputes the name every tick, and
  `showWaitingTimer` no longer bails permanently when the name is
  momentarily unresolvable.
- **VAvatar indicator rework (mobile client).** Old: cyan turn ring and lime
  priority ring drawn at the same rect/thickness — overdrew each other, read
  as one muddy greenish outline; priority ring gated to all-human games.
  New: gold outer ring = turn player; green inset ring = the game is waiting
  on this player, keyed on `AwaitingInput` — correct during combat, shown for
  yourself, and shown in AI games too (the flag only ever sets for humans, so
  no AI flicker; gate removed). A ~3-cycle pulse via `ForgeAnimation` grabs
  the eye when the wait lands, then holds steady — continuous rendering
  self-releases after the burst (the Chronicle reveal-scene leak lesson).
- Desktop suite 424 green, mobile-dev jar boots clean (25s, no exceptions).
  Committed + pushed; worklist doc updated with the entry. Unreleased — the
  next release cut carries it.
